default** (used until answered). Record answers here and update the affected
spec section; do not silently change behaviour.

| `Q-18` | Power-on window: for a few seconds after power-on, until the firmware applies its pin settings, the relay pins are pulled low. | `Q-19` | Relative file paths in the configuration (e.g. `recipes.file`): resolve against the configuration file's directory or the working directory? | **Answered 2026-10-11:** the configuration file's directory (also when the default `./config.json` is missing). | `NFR-020`, `RCP-001` |

| `Q-21` | Default configuration path without `--config` (`NFR-020` says "next to the application", which is undefined for an installed Python package)? | **Answered 2026-10-11:** `config.json` in the working directory; if it is missing, the built-in defaults. | `Q-22` | Recipe file does not exist? | **Answered 2026-10-11:** if `recipes.file` is not set, use the legacy catalogue shipped with the application (identical to `data/recipes.json`); if it is set and the file is missing, refuse to start. Replaced by `Q-29`: a missing recipe directory is created with the shipped recipes. | `RCP-001`, `RCP-003` |
| `Q-23` | `GOAL-005` iodine test progress outside the additional rest is "0, `Waiting for answer`" — also when the goal is `Waiting` or `Done`? | **Answered 2026-10-11:** only while `Active` in the asking phase; `Waiting` and `Done` use the default progress of `DOM-022` (`0%` / `100%`). | `GOAL-005`, `DOM-022` |
| `Q-24` | Chart thinning (`IF-043`) removes point i+1 of the smallest gap, which is usually the **newest** point: with 1 s sampling the newest chart point lags the current time by about 15 s after one hour and about 30 s after six hours (the current temperature itself is always shown in the hardware status). | `Q-25` | ADR-0001 says the GPIO chip is found by label "(`pinctrl-bcm2835` / `pinctrl-bcm2711` / `pinctrl-rp1`, configurable)", but [data/config.schema.json](data/config.schema.json) has no key for the chip label. | `Q-26` | Heater relay type: in the duty cycle (`CTL-042`, minimum phase 500 ms) the heater relay switches on and off about once per second at 50 % power, which is used within 3 K below the target and during the boil (`CTL-012`, `Q-04`). A mechanical relay wears out quickly at that rate. Should a solid-state relay be required or recommended for the heater, and should the default heating configuration change with it? | **Answered 2026-10-12:** keep a normal (mechanical) relay, active-low as in `HW-011`. To reduce wear the duty cycle becomes slower: 10 s on + 10 s off at 50 %, other powers scaled the same way. Answered 2026-10-13: other powers keep the `CTL-042` formula with a 10 s minimum phase (not a fixed 20 s period); the `TOOL-002` duty-cycle mode holds each step for two periods. Done in [issue #33](https://github.com/tinkerius/brewberrypi-app/issues/33): `minPhaseMilliseconds` default 10000, `[FIX-26]`. | `HW-011`, `CTL-042`, `CTL-046` |
| `Q-27` | Recipes in one file (`recipes.json`) or one file per recipe? | **Answered 2026-10-15:** one file per recipe in a recipe directory (`recipes.directory`, default `recipes`). The file name `<id>.json` is the recipe id; the file has no `id`. The recipe list is sorted by id. An invalid file is logged and skipped instead of stopping the start. `recipes.file` is removed (no installation uses it yet). This also replaces `recipes.file` in the answers to `Q-19` and `Q-22`. | `RCP-001`, `RCP-002`, `RCP-003`, `AC-080`, `AC-081` |
| `Q-28` | Client/server interface: one bidirectional channel with periodic broadcasts and fire-and-forget commands (legacy topics), or request/response for reads and commands plus a push channel for changes? | **Answered 2026-10-17:** request/response for reads and commands, each with exactly one reply and an outcome (accepted, invalid, not found, conflict, forbidden); push only for changes, starting with a snapshot, plus a heartbeat. A paused process continues with a new command `resume` (`start` no longer resumes). An answer names the request it answers. Same-origin rule (`Q-17`). Transport: REST + server-sent events ([ADR-0002](../adr/0002-rest-and-server-sent-events.md)). | `IF-001..076`, `ENG-012`, `ENG-016`, `DOM-035`, `UI-041`, `UI-050`, `UI-060` |
| `Q-29` | The brewer adds a recipe file on the device, but the application only reads recipes at startup and uses its built-in catalogue while no recipe directory exists. Who creates the configuration file and the recipe directory, and must a new recipe need a restart? | **Answered 2026-10-23:** the application owns its configuration directory (on BrewberryPi OS: the folder `config/app`, which the brewer can edit over the network). It reads recipes only from the recipe directory; there is no built-in fallback. A missing recipe directory is created with the shipped recipes, so a first start already has recipes; recipes the brewer deletes are not written again. A missing configuration file is written with every key at its default. The recipe directory is watched: added, changed and removed recipe files reach every client without a restart; a loaded process keeps its recipe. Files the application writes are group-writable. No migration of existing installations. | `RCP-001`, `RCP-006`, `NFR-020`, `NFR-021`, `NFR-031`, `NFR-032`, `AC-084..086` |
| `Q-30` | On BrewberryPi OS the app is reached on port 80 (the OS forwards it to `server.port`), so `http://<host>/` no longer opens the device web interface on port 8081. Should the app's UI link to it? | **Answered 2026-10-23:** yes, a link `Device settings` in the top bar, opened in a new tab; its address is configurable (`ui.deviceLink`, default `http://{host}:8081/`, empty: no link). | `UI-002`, `IF-080`, `AC-093` |
| `Q-31` | Recipe files are to hold recipe design information later (e.g. grain bill, hops), not only the mash process. How is the file laid out, and are files in the old flat format still read? | **Answered 2026-10-30:** the goals move into the section `mashing_process` (`{"name": …, "mashing_process": {"goals": […]}}`); design sections are added next to it later. Only the new format is valid: a file with `goals` at the top level is skipped with an error saying to move them into `mashing_process`. The recipe detail message (`IF-031`) keeps `goals` at the top level. | `RCP-001`, `RCP-003`, `RCP-007`, `DOM-001`, `IF-031`, `AC-094` |
| `Q-32` | Which recipes does the application ship? The legacy catalogue holds 8, most of them the product owner's personal brew recipes. | **Answered 2026-10-30:** only `BENIWEISS` and `WaterBoil`; the other 6 are removed from the repository and its history. The acceptance tests use their own test recipes `DEMO` and `IODINE`, which are not shipped (07 §7.5). | `RCP-002`, `07-recipes.md` §7.4/§7.5, `AC-030`, `AC-037`, `AC-053`, `AC-058`, `AC-078`, `AC-080`, `AC-084`, `AC-090`, `AC-091` |
| `Q-33` | The recipe file format will change again (e.g. design sections next to `mashing_process`, `Q-31`), not always backwards compatibly. How does the application recognise a file's format and read files in an older one? | **Answered 2026-11-06:** every recipe file states its format version, `version` (1, 2, 3, …; a file without it is in version 1, today's format). A file in a newer version than the application knows is not read. Every change of the format, also one that only adds something, raises the version by one and adds a migrator from the previous version; a file in an older version is migrated one version at a time to the latest and written back to its file, the original kept as a copy in `.backup`. After an application rollback, recipes already migrated to a newer version are skipped until the copies are put back. | `RCP-003`, `RCP-007`..`RCP-011`, `AC-095`..`AC-099` |
| `Q-34` | A recipe always needs at least one goal, so a recipe that is still being written (in the recipe editor, `Q-09`) or that only holds design information later (`Q-31`) cannot be a valid file. Should recipes without goals be allowed? | **Answered 2026-11-06:** yes. `mashing_process.goals` may be empty; the section `mashing_process` stays required. This changes the format: version 2, migrator `1 → 2` changes nothing but the version (`RCP-011`). A recipe without goals is listed like any other and its details can be read, but it cannot be loaded: `load` is rejected with `Recipe <name> (<id>) has no goals.` (outcome conflict), and a loaded process stays loaded. | `DOM-001`, `RCP-007`, `RCP-008`..`RCP-011`, `ENG-010`, `IF-052`, `AC-095`, `AC-100`, `AC-101` |
| `Q-35` | Recipes are to be synced with a cloud store that a separate recipe editor uses (the editor and its backend are not part of this application). The application owns the recipe directory, its format version and migration (`RCP-001`, `RCP-006`..`RCP-011`), so the sync client on the device would be part of the application. How does the sync work? To decide: direction (pull only, or two-way); the conflict rule when a recipe also changed locally (files edited over the network, `Q-29`, and migrated files written back, `RCP-010`); recipes in a newer format version than the device reads (`RCP-009`); where the credentials are kept (in `config.json`, which is in the brewer's network share on BrewberryPi OS, or a separate secrets mount, which needs runtime contract version 3); behaviour while offline; that a sync never changes the recipe of a loaded process (`RCP-006`). | **Answered 2026-11-06:** one way only, from the cloud to the device; the device never writes to the cloud. The feature is called **Cloud Sync**; the only provider so far is **Google Drive**, where the recipe editor saves recipes. While Cloud Sync is connected, the recipe directory mirrors the cloud folder: local changes are overwritten (a copy is kept in `.backup`), deleted files come back, files that are not in the cloud are moved to `.backup`, and a notice file in the directory says not to edit there. On disconnect the files stay as ordinary recipe files. The sign-in is stored in the configuration directory, which is in the brewer's network share on BrewberryPi OS (accepted). Spec [14](14-cloud-sync.md), design [ADR-0003](../adr/0003-cloud-sync.md). | `OV-008`, `RCP-001`, `RCP-004`, `SYNC-001`..`SYNC-030`, `IF-090`, `IF-091`, `UI-080`..`UI-085`, `AC-102`..`AC-116` |
| `Q-36` | Several changes of the recipe file format can come one after another before the next release of the application (e.g. more recipe information, `Q-31`). Does each of them raise the format version (`RCP-011`)? | **Answered 2026-11-10:** no. The version is raised only once between two releases of the application (a pre-release counts): the first format change after a release raises it by one, every further change before the next release amends that unreleased version (its schema, its migrator, its row in the version table, the shipped recipes and the migration's acceptance criteria) instead of adding another. | `RCP-011`, spec 7.2.1 |
| `Q-37` | The recipe editor gets a tab **Mashing**, where the brewer plans the mash: from a list of common rests (pre-mash, acid, beta-glucan, ferulic acid, protein, maltose, combined, saccharification, mash-out) the brewer picks the rests to do, each with its temperature and duration. How is the plan kept in the recipe file, and what does the application do with it? | **Answered 2026-11-10:** in the optional top-level section `mashing`, an object keyed by rest id, each rest at most once, each with `temperature` and `minutes` (`{"MaltoseRest": {"temperature": 63, "minutes": 45}}`). This changes the format: version 3, migrator `2 → 3` changes nothing but the version (`RCP-011`). | `DOM-001`, `RCP-007`, `RCP-011`, `RCP-012`, `AC-101`, `AC-118`, `AC-119` |
| `Q-38` | The recipe editor gets a tab **Ingredients** (opened first) with a table of malts and one of hops: each entry a name and an amount in grams, with its share of the total weight and a sum line. The application accepts it and does not use it. Format version 3 is amended, not raised (`Q-36`: no release since version 2). | `DOM-001`, `RCP-007`, `RCP-011`, `RCP-013`, `AC-120` |
| `Q-39` | The recipe editor shows the beer colour (from each malt's EBC) and the bitterness (from each hop's alpha acid and boil time), which also need the batch volume and the original gravity. Format version 3 is amended, not raised (`Q-36`). | `DOM-001`, `RCP-007`, `RCP-011`, `RCP-013`, `RCP-014`, `AC-121` |
| `Q-40` | The recipe editor gets a tab **Water** with the brewing-day water volumes: mash water, sparge water and top-up water (after lautering, to reach the original gravity). | `Q-42` | Besides hops, other things go into the boil (Irish moss, spices, yeast nutrient).
