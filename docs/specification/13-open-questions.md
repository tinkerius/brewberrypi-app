# 13 — Open Questions

Decisions for the product owner. Each question states the **current spec
default** (used until answered). Record answers here and update the affected
spec section; do not silently change behaviour.

| ID | Question | Current default in spec | Affects |
|---|---|---|---|

| `Q-02` | After `Stopped`/`Finished`, should **Start** restart the recipe from the beginning (implicit reload) instead of being rejected? | Rejected; brewer must load again | `ENG-012` |
| `Q-03` | Should **MashIn** (and PourInBrewingWater) hold the temperature of the preceding HeatUp while waiting for confirmation? Legacy does not (temperature drifts down; pump keeps running). | Legacy behaviour: no temperature control, actuators unchanged | `GOAL-001`, `GOAL-003` |
| `Q-04` | Boil (`CookWater`, target 100 °C) runs at 50 % heating because of the near-target band. Intended, or should boiling use full power / a configurable boil power? | Legacy behaviour (50 %) | `GOAL-008`, `CTL-012` |

| `Q-09` | Recipe management in the UI (create/edit/delete)? | No — file only | `RCP-004` |
| `Q-10` | Any access protection (PIN/password) for the web UI? | None (trusted LAN) | `IF-060` |
| `Q-11` | Show successful command replies as modal (legacy intent) or as non-blocking toast? | Modal for all replies | `UI-050` |
| `Q-12` | Over-temperature cut-off (e.g. heater off above a configurable max temperature when not boiling) — desired as additional safety? | Not included (not in legacy) | `NFR-001` |
| `Q-13` | Recipes are incomplete (end after heat-up for lautering; lautering & boil never modelled). Complete them in phase 2? | Keep as-is | `07-recipes.md` |
| `Q-14` | Should the chart persist across server restarts / be exportable (CSV)? | No | `IF-042` |
| `Q-15` | In legacy the pump is switched on by every temperature-controlling goal and only switched off by Lautering / stop / finish. Any need for pump-off phases (e.g. during mash-in)? | Legacy behaviour | `CTL-010` |
| `Q-16` | `[NEW]` Software update from the web UI: should the brewer be able to see installed and available application versions, install or select one, and roll back? It would be allowed only while no process is loaded. The update itself is carried out by the operating-system side (see ADR-0001). | Not part of the application; versions are changed with the operating-system tooling only | `09-user-interface.md`, `08-client-server-interface.md`, `IF-060`, `NFR-023` |
| `Q-17` | `[NEW]` Cross-origin protection: without authentication, any web page opened in a browser on the same LAN can send commands to the server, for example through a cross-site WebSocket. Should the server reject connections and commands whose origin is not its own web UI? | **Answered 2026-10-17 (with `Q-28`):** yes. Requests and push connections from another origin are refused, and commands must be sent as JSON (`IF-061`). | `IF-002`, `IF-060`, `Q-10` |
| `Q-18` | Power-on window: for a few seconds after power-on, until the firmware applies its pin settings, the relay pins are pulled low. Low is the "on" level of the active-low relays; whether a relay actually switches depends on the relay board. Accept this as a documented limitation, or require a hardware change (pull-ups on the relay inputs)? | Accepted limitation: pins set to off as early as the firmware allows, behaviour measured in the hardware tests (M9/M12) | `NFR-001`, `NFR-002`, `HW-020` |
| `Q-19` | Relative file paths in the configuration (e.g. `recipes.file`): resolve against the configuration file's directory or the working directory? | **Answered 2026-10-11:** the configuration file's directory (also when the default `./config.json` is missing). | `NFR-020`, `RCP-001` |
| `Q-20` | Target platform: `NFR-050` says 32- or 64-bit ARM. Raspberry Pi 3, 4 and 5 all run 64-bit Raspberry Pi OS, and the planned BrewberryPi OS image is 64-bit only. Drop 32-bit support? | 64-bit only | `NFR-050` |
| `Q-21` | Default configuration path without `--config` (`NFR-020` says "next to the application", which is undefined for an installed Python package)? | **Answered 2026-10-11:** `config.json` in the working directory; if it is missing, the built-in defaults. Changed by `Q-29`: a missing file is written with the defaults. | `NFR-020` |
| `Q-22` | Recipe file does not exist? | **Answered 2026-10-11:** if `recipes.file` is not set, use the legacy catalogue shipped with the application (identical to `data/recipes.json`); if it is set and the file is missing, refuse to start. Replaced by `Q-29`: a missing recipe directory is created with the shipped recipes. | `RCP-001`, `RCP-003` |
| `Q-23` | `GOAL-005` iodine test progress outside the additional rest is "0, `Waiting for answer`" — also when the goal is `Waiting` or `Done`? | **Answered 2026-10-11:** only while `Active` in the asking phase; `Waiting` and `Done` use the default progress of `DOM-022` (`0%` / `100%`). | `GOAL-005`, `DOM-022` |
| `Q-24` | Chart thinning (`IF-043`) removes point i+1 of the smallest gap, which is usually the **newest** point: with 1 s sampling the newest chart point lags the current time by about 15 s after one hour and about 30 s after six hours (the current temperature itself is always shown in the hardware status). Keep, or never remove the newest point? | Keep (`IF-043` as specified) | `IF-043`, `UI-020` |
| `Q-25` | ADR-0001 says the GPIO chip is found by label "(`pinctrl-bcm2835` / `pinctrl-bcm2711` / `pinctrl-rp1`, configurable)", but [data/config.schema.json](data/config.schema.json) has no key for the chip label. Add a configuration key (e.g. `hardware.gpioChipLabel`)? | No key: the three known labels (Raspberry Pi 3, 4, 5) are searched | `HW-010`, `NFR-050` |
| `Q-26` | Heater relay type: in the duty cycle (`CTL-042`, minimum phase 500 ms) the heater relay switches on and off about once per second at 50 % power, which is used within 3 K below the target and during the boil (`CTL-012`, `Q-04`). A mechanical relay wears out quickly at that rate. Should a solid-state relay be required or recommended for the heater, and should the default heating configuration change with it? | **Answered 2026-10-12:** keep a normal (mechanical) relay, active-low as in `HW-011`. To reduce wear the duty cycle becomes slower: 10 s on + 10 s off at 50 %, other powers scaled the same way. Answered 2026-10-13: other powers keep the `CTL-042` formula with a 10 s minimum phase (not a fixed 20 s period); the `TOOL-002` duty-cycle mode holds each step for two periods. Done in [issue #33](https://github.com/tinkerius/brewberrypi-app/issues/33): `minPhaseMilliseconds` default 10000, `[FIX-26]`. | `HW-011`, `CTL-042`, `CTL-046` |
| `Q-27` | Recipes in one file (`recipes.json`) or one file per recipe? | **Answered 2026-10-15:** one file per recipe in a recipe directory (`recipes.directory`, default `recipes`). The file name `<id>.json` is the recipe id; the file has no `id`. The recipe list is sorted by id. An invalid file is logged and skipped instead of stopping the start. `recipes.file` is removed (no installation uses it yet). This also replaces `recipes.file` in the answers to `Q-19` and `Q-22`. | `RCP-001`, `RCP-002`, `RCP-003`, `AC-080`, `AC-081` |
| `Q-28` | Client/server interface: one bidirectional channel with periodic broadcasts and fire-and-forget commands (legacy topics), or request/response for reads and commands plus a push channel for changes? | **Answered 2026-10-17:** request/response for reads and commands, each with exactly one reply and an outcome (accepted, invalid, not found, conflict, forbidden); push only for changes, starting with a snapshot, plus a heartbeat. A paused process continues with a new command `resume` (`start` no longer resumes). An answer names the request it answers. Same-origin rule (`Q-17`). Transport: REST + server-sent events ([ADR-0002](../adr/0002-rest-and-server-sent-events.md)). | `IF-001..076`, `ENG-012`, `ENG-016`, `DOM-035`, `UI-041`, `UI-050`, `UI-060` |
| `Q-29` | The brewer adds a recipe file on the device, but the application only reads recipes at startup and uses its built-in catalogue while no recipe directory exists. Who creates the configuration file and the recipe directory, and must a new recipe need a restart? | **Answered 2026-10-23:** the application owns its configuration directory (on BrewberryPi OS: the folder `config/app`, which the brewer can edit over the network). It reads recipes only from the recipe directory; there is no built-in fallback. A missing recipe directory is created with the shipped recipes, so a first start already has recipes; recipes the brewer deletes are not written again. A missing configuration file is written with every key at its default. The recipe directory is watched: added, changed and removed recipe files reach every client without a restart; a loaded process keeps its recipe. Files the application writes are group-writable. No migration of existing installations. | `RCP-001`, `RCP-006`, `NFR-020`, `NFR-021`, `NFR-031`, `NFR-032`, `AC-084..086` |
| `Q-30` | On BrewberryPi OS the app is reached on port 80 (the OS forwards it to `server.port`), so `http://<host>/` no longer opens the device web interface on port 8081. Should the app's UI link to it? | **Answered 2026-10-23:** yes, a link `Device settings` in the top bar, opened in a new tab; its address is configurable (`ui.deviceLink`, default `http://{host}:8081/`, empty: no link). | `UI-002`, `IF-080`, `AC-093` |
| `Q-31` | Recipe files are to hold recipe design information later (e.g. grain bill, hops), not only the mash process. How is the file laid out, and are files in the old flat format still read? | **Answered 2026-10-30:** the goals move into the section `mashing_process` (`{"name": …, "mashing_process": {"goals": […]}}`); design sections are added next to it later. Only the new format is valid: a file with `goals` at the top level is skipped with an error saying to move them into `mashing_process`. The recipe detail message (`IF-031`) keeps `goals` at the top level. | `RCP-001`, `RCP-003`, `RCP-007`, `DOM-001`, `IF-031`, `AC-094` |
